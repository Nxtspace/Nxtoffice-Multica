## 技术栈建议（ADR-02，提议）

**前提**：Web 浏览器为交付端、项目尚无既有仓库/框架约束；2D 与 3D 同期、同轮验收，共用上一条 ADR 的状态与权限契约。若项目方要求原生端或团队已有稳定前端栈，应重评本选型。

| 层 | 建议 | 取舍 |
|---|---|---|
| 应用外壳与详情 | TypeScript + React + Vite；详情、权限不足、断线与过期提示用 DOM | 两视图共享路由、详情和状态层；Vite 有官方 React/TS 模板（[文档](https://vite.dev/guide/)） |
| 2D 等距场景 | PixiJS，首选 WebGL 渲染精灵与交互热点 | 适合大量 2D 对象；PixiJS 官方将 WebGL 列为生产推荐，WebGPU 尚需谨慎（[文档](https://pixijs.com/guides/components/renderers/)） |
| 3D 场景 | Three.js + React Three Fiber，首选 WebGL | 复用 React 状态与交互模型；R3F 是 Three.js 的 React 渲染器（[文档](https://r3f.docs.pmnd.rs/getting-started/introduction)）。3D 资源按场景加载，不让 2D 入口承担其下载与 GPU 成本 |
| 共享状态 | 独立 TypeScript 契约包：对象 ID、关系边、源状态、快照版本、更新时间、权限裁剪结果；2D/3D 各自只负责投影 | 不在两套渲染器里分别推导"工作中/阻塞"；详情按对象重新鉴权 |
| 服务端适配 | 若取得正式授权读取入口，建议 Node.js + TypeScript + Fastify，按用户鉴权并输出版本化快照/详情；请求与响应使用 JSON Schema 校验（[文档](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)） | 暂不引入数据库、Redis 或消息队列；事件流、SSE/轮询须在平台事件与限流契约验证后决定，不能用当前 owner CLI 当生产数据接口 |
| 验证 | Playwright 跑同一真实数据脚本的 2D/3D 核对、断线和越权路径（[文档](https://playwright.dev/docs/intro)）；另做目标设备的对象数与帧率小样 | 浏览器/设备矩阵、对象规模和性能阈值由产品与项目方批准 |

**选型判据**（5 分制，越高越好；2D 表达 25%、3D 表达 25%、共享契约 20%、性能可控 15%、维护成本 15%）：PixiJS＋R3F 为 5/5/4/4/3，**4.35**；全部用 Three.js 为 3/5/4/3/4，**3.85**；手写 Canvas 2D＋Three.js 为 3/4/3/2/2，**2.95**。推荐前者；代价是维护两套渲染库，但状态、权限与详情只维护一套。全 Three.js 的 2D 资产/交互适配负担较高；手写 Canvas 的命中测试和性能治理成本更高。评分是基于当前需求的工程判断，尚非压测结果。

**采纳门槛与退出条件**：前端负责人确认能维护 PixiJS 与 R3F，后端负责人确认 Fastify 或提出既有服务栈；最小样同时渲染产品确认的 Agent/关系数量，在目标设备上测帧率、内存与切换耗时。若现有仓库栈、团队技能或性能数据推翻上述假设，保留共享契约与服务端授权边界，重评具体框架。平台正式入口与受限用户权限测试未通过前，不批准适配器进入实现。

**我需要谁在什么时间点做什么决定**：项目方与产品经理在冻结验收脚本前确认 Web/设备范围、场景规模和性能门槛；前端、后端负责人在建仓或开工前确认维护人及既有技术栈；平台接口负责人在适配开工前交付正式读取、授权和限流契约，项目经理据验证结果编排两条场景线。
